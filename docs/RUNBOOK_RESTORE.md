# VOWS Studio — Backup & Disaster Recovery Runbook
**Document Ref:** `docs/RUNBOOK_RESTORE.md`  
**Compliance Standards:** SECURITY_PLAN §11, §15, DECISION_LOG D-43  
**Review Frequency:** Quarterly Restoration Drill  

---

## 1. Overview & Architecture

VOWS Studio operates on a dual-tier backup strategy to ensure zero data loss and business continuity:
1. **Tier 1 (Supabase Pro Physical Backups):** Automated daily physical backups with Point-In-Time Recovery (PITR) up to 7 days.
2. **Tier 2 (Logical Export & Storage Snapshot):** Nightly pg_dump / logical export of critical operational partitions stored in an isolated external cloud storage bucket (AES-256-GCM encrypted).
3. **Tier 3 (Pre-Destructive Action Archives):** Automated pre-reset logical snapshots generated by the Data Management engine before any purge operation.

---

## 2. Backup Schedules

| Scope | Frequency | Retention | Storage Target | Encryption |
|---|---|---|---|---|
| Postgres PITR (WAL) | Continuous | 7 Days | Supabase Managed | AES-256 |
| Daily Logical Schema Export | Daily @ 02:00 IST | 30 Days | AWS S3 / Cloudflare R2 | AES-256-GCM |
| Media & Document Buckets | Weekly sync | 90 Days | Offsite Archive | AES-256 |
| Pre-Reset Snapshots | On-demand before wipe | Permanent | `documents` bucket | AES-256-GCM |

## 3. Step-by-Step Restoration Drill (Scratch Recovery)

Follow this procedure to reconstruct the VOWS Studio database from scratch on a new Postgres cluster.

### Phase 1: Environment Provisioning
1. Provision a fresh Supabase Pro or Postgres 15+ instance.
2. Ensure timezone is set to `UTC` (application layer calculates `Asia/Kolkata` IST).
3. Note the database connection string:
   ```bash
   export RESTORE_DB_URL="postgresql://postgres:[PASSWORD]@[HOST]:5432/postgres"
   ```

### Phase 2: Schema Migration & Custom Types
Apply base migrations in sequential dependency order:
```bash
# 1. Connect to repository
cd /path/to/vows-studio

# 2. Run Supabase migration suite
npx supabase db push --db-url "$RESTORE_DB_URL"
```

Verify that all essential tables and extensions are created:
- `auth.users`, `public.profiles`, `public.business_settings`
- `public.clients`, `public.quotations`, `public.bookings`, `public.events`
- `public.invoices`, `public.payments`, `public.credit_notes`, `public.expenses`
- `public.delivery_pipelines`, `public.reviews`, `public.audit_log`

### Phase 3: Data Restoration from Logical Archive
1. Download the latest encrypted backup archive:
   ```bash
   aws s3 cp s3://vows-studio-backups/prod/latest.sql.gz.enc ./latest.sql.gz.enc
   ```
2. Decrypt archive using the master disaster recovery key:
   ```bash
   openssl enc -d -aes-256-gcm -pbkdf2 -in latest.sql.gz.enc -out latest.sql.gz -pass env:DR_MASTER_KEY
   gunzip latest.sql.gz
   ```
3. Temporarily bypass immutability triggers during restore:
   ```sql
   -- Set transaction-local reset flag to allow trigger bypass
   SET LOCAL app.reset_in_progress = 'on';
   ```
4. Restore data using psql:
   ```bash
   psql "$RESTORE_DB_URL" -f latest.sql
   ```

### Phase 4: Sequence Counter Synchronization
Ensure serial and document sequence counters do not collide with restored primary keys:
```sql
SELECT setval('quotations_quotation_number_seq', (SELECT MAX(id) FROM quotations));
SELECT setval('invoices_invoice_number_seq', (SELECT MAX(id) FROM invoices));
SELECT setval('payments_receipt_number_seq', (SELECT MAX(id) FROM payments));
```

### Phase 5: Storage Asset Re-linking
1. Sync storage buckets from the backup bucket:
   ```bash
   aws s3 sync s3://vows-studio-backups/storage/documents/ s3://vows-supabase-documents/
   aws s3 sync s3://vows-studio-backups/storage/portfolio/ s3://vows-supabase-portfolio/
   ```

## 4. Post-Restore Financial Integrity Verification

Execute the following SQL queries to ensure zero financial drift:

```sql
-- 1. Check Invoice vs Payment reconciliation
SELECT 
  i.id AS invoice_id,
  i.invoice_number,
  i.total_paise,
  COALESCE(SUM(p.amount_paise), 0) AS total_paid_paise,
  i.balance_paise,
  (i.total_paise - COALESCE(SUM(p.amount_paise), 0)) AS calculated_balance
FROM invoices i
LEFT JOIN payments p ON p.invoice_id = i.id AND p.status = 'cleared'
GROUP BY i.id
HAVING i.balance_paise != (i.total_paise - COALESCE(SUM(p.amount_paise), 0));
-- Expected result: 0 rows

-- 2. Check Ledger double-entry balance
SELECT 
  SUM(CASE WHEN type IN ('invoice_issued', 'manual_income') THEN amount_paise ELSE 0 END) AS total_inflow,
  SUM(CASE WHEN type IN ('expense', 'crew_payout') THEN amount_paise ELSE 0 END) AS total_outflow
FROM ledger_entries_v;

-- 3. Verify RLS is active on all restored tables
SELECT tablename, rowsecurity 
FROM pg_tables 
WHERE schemaname = 'public' AND rowsecurity = false;
-- Expected result: 0 rows
```

## 5. RTO & RPO Objectives

- **Recovery Point Objective (RPO):** < 15 minutes (using PITR WAL logs) or < 24 hours (cold logical snapshot).
- **Recovery Time Objective (RTO):** < 45 minutes for full database and application failover.
- **Drill Cadence:** Conduct a cold restore into a staging environment once every 90 days. Record drill execution logs in `docs/RELEASE_CHECKLIST.md`.
